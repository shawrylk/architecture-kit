# Split work across PCs

Fleet assigns free open issues with a shared node list and an optional node server. Nothing about the PCs is written to GitHub. Install `architecture-harness` and authenticate `gh` on each PC. Give each PC its own id. Run this on PC a1, then repeat on b2 and c3 with only `--self` changed:

```sh
npx qc fleet init --self a1 --nodes a1:1:L,b2:1:L,c3:2:L
npx qc fleet status --repo shawrylk/architecture-kit
npx qc fleet next --repo shawrylk/architecture-kit
```

Keep the same `nodes` on all PCs. Weight 2 receives about twice as much work as weight 1. `maxSize` is S, M or L; a node accepts issues up to that size. `active` defaults to true. Labels `size:S`, `size:M` and `size:L` ignore case; an issue without one is M. Ownership depends on the repository, issue number and shared nodes, so the PCs agree. `next` prints this PC's oldest five free issue numbers; `--all` prints every one. It exits 3 with `no free issue for <self>` when none remain; errors exit 1. `status` prints weight, maxSize, active, free count and up to ten numbers per node, then taken and unassigned counts. It shows up to 14 nodes and reports omitted nodes, then adds `node=running|stopped|stale leader=<id or unknown> peers=<seen in 90 s>/<other nodes>`.

`QC_FLEET_FILE` overrides the settings path; without a file fleet is off. `--repo` defaults to origin. Otherwise Windows uses `%APPDATA%\qc\fleet.json`; other systems use `$XDG_CONFIG_HOME/qc/fleet.json` or `~/.config/qc/fleet.json`. The file contains `{ "self": "a1", "nodes": [{ "id": "a1", "weight": 1, "maxSize": "L", "active": true }] }`. `init` creates parent folders and uses mode 0600 on POSIX; an existing file needs `--force` to replace it.

Optional `secret` is shared hex text of at least 64 characters; `init --secret <hex>` reuses it, otherwise init generates 32 random bytes and prints a line to pass the same secret on the other PCs. Optional `leaders` lists node IDs in preference order (default: node order). Each node may have `address` (a host other than `0.0.0.0` or `::`) and `port` (1024–65535); set these with `--addresses a1@host:8080,b2@[::1]:8081`. Old files remain valid. Signed messages are data; local state stays in `<git common dir>/qc/fleet/`. `qc fleet start [--leader]` detaches `qc fleet serve`, logging to `<state dir>/node.log`; it needs a secret and this node's address (port defaults to 8080), passes a random instance token to the child, saves it with the PID in `node.json`, waits up to 5 seconds for matching health, and succeeds if that instance is already running. `status` and `stop` require health to match the saved instance; a mismatch reports `stale` and leaves the process alone. `qc fleet stop` waits up to 5 seconds for exit and removes only `node.json`. Other state survives, including `outbox.json` and `peers.json`. `serve [--leader]` also runs in the foreground.

Free issues exclude `hold`, `merge.holdLabel` and `fleet-skip`. An open PR body naming `#<number>`, a PR head branch, or an origin branch named `<prefix>/<number>-...` makes an issue taken. Reads use `gh` and git, bounded to 500 open issues and 200 open PRs. No qualifying active node means unassigned. Only a matching local checkout supplies `merge.holdLabel` from `qc.config.json`. The server binds only its configured address. `GET /health` returns `{"ok":true,"instance":"<token>"}`; `POST /message` checks signatures and saved replay IDs, accepts up to 64 KB with 202, puts work messages into `queue.json`, and never runs commands. Requests time out after 10 seconds; shutdown stops accepting requests and force-closes open connections after 1 second. Other routes return 404; bad messages return 400 and oversized bodies 413.

For free-issue suggestions without a Leader, set `active: false` on every PC to redistribute that node's suggestions. Saved Leader assignments remain until their issues close; automatic takeover is outside this flow. Push the usual issue branch when starting work so subsequent free-issue reads see it as taken. Every 30 seconds, heartbeats send `{ kit: <kit commit or null>, leader: <boolean> }` to other active addressed nodes; `peers.json` records receipt times; heartbeats never enter `queue.json`. State files are `assignments.json`, `questions.json`, `seen.json`, `queue.json`, `outbox.json`, `dead.json`, `peers.json` and `node.json`. Sends time out after 5 seconds; network errors and 5xx replies enter `outbox.json` and retry oldest first after 1 second, doubling to 60 seconds. The outbox stores unsigned fields and a fixed ID; every send signs again with the current time. A 4xx reply removes the entry: `seen-id` counts as delivered; other refusals enter `dead.json`, which keeps only the last 100.

With `serve --leader`, an assignment tick runs every 60 seconds. It reads `freeIssues` and open issue numbers through `gh`; a failed read skips that tick. The Leader saves `{repo, issue, node, epoch: 1, time}` records keyed by `repo#issue` in `assignments.json`, retaining each until its issue closes. GitHub labels stay unchanged. It considers `ci-red` issues first, then the lowest issue number, using `ownerOf(repo, issue, size, idle live nodes)` and skipping issues with no owner. Each node gets one issue at a time. Other nodes must be active, addressed, and have a heartbeat at most 90 seconds old; the Leader itself is always live. A different heartbeat kit blocks new work and warns `node <id> runs kit <k>, leader runs <k>`. On every 60-second assignment tick, the Leader sends an `assign` message with `{issue, epoch}` for each current assignment to another live node, including previously sent assignments. It skips a repeat when that node already has an `assign` for the same repository, issue and epoch in `outbox.json`. The Leader writes all these messages to the outbox before sending any of them, then flushes the outbox. Stopping during a send leaves unconfirmed assignments queued for retry. Every node tick accepts only positive integer issues and epochs from a peer whose latest heartbeat says `leader: true`; a higher epoch replaces a lower one, and the same issue and epoch is ignored without changing the saved assignment. An assign arriving before that peer has a Leader claim stays in `queue.json` until a heartbeat claims leadership. With no claim it expires after 10 minutes from its message time; a `leader: false` heartbeat drops it at once on the next node tick. The Leader sends a fresh message on the next assignment tick, so an unclaimed assignment dropped after 10 minutes can arrive again. Other queued message kinds remain. Every 60 seconds, a follower reads `gh issue list --state open` for each repository where it holds assignments and removes its own assignments whose issues have closed. A failed or unreadable gh response preserves that repository's assignments. Only the serve loop writes `assignments.json`. `qc fleet next` reads the file and makes the same open-issue check to hide closed issues from its output without writing the file. On a gh error it uses the saved assignments unchanged. It prints open saved assignments for this node and repository first as `#<issue> epoch=<n>`; with none, its usual free-issue output applies. Takeover and a special ci-red owner rule are outside this assignment flow.

`qc fleet plan <issue> --file <path>` and `qc fleet ask <issue> --file <path>` require an issue held by this node. Files hold at most 20000 characters. Both send `{issue, epoch, text}` to the peer whose heartbeat says `leader: true`; plan sends kind `plan` and posts a signed Coder role comment with kind `plan` and ref `#<issue>`, while ask sends kind `question` and posts nothing. Both write the message to `outbox.json` before any network send, then call `flushOutbox`; the plan comment follows the outbox write. Commands print their message IDs.

`qc fleet approve <message-id> [--changes] [--file <note>]` runs on the Leader only. It sends `{issue, epoch, plan: <id>, approved: !changes, note}` to the plan sender and posts a signed Leader role comment of kind `approve`. Without a file the note is empty; `--changes` requests changes.

`qc fleet answer <message-id> --file <answer>` runs on the Leader only. It sends `{issue, epoch, question: <id>, text}` to the question sender and posts a signed Leader role comment of kind `answer` with every question line quoted. Before either reply reads a file, posts a comment or sends a message, it checks the request by the same rule as the Leader tick: the sender must hold that repository and issue at that epoch in the Leader assignments. A failed check drops the request, prints the reason and exits 1 without a comment or send. Both replies remove the request from the Leader queue; transient send failures use the durable outbox. A failed comment leaves the request queued.

Each Leader tick drops plans and questions unless the sender holds that repository, issue and epoch. Followers apply the `assign` sender rule to approvals and answers: unknown Leader claims wait up to ten minutes, explicit false claims drop replies. Wrong epochs or issues not held by this node drop immediately. Each accepted reply also appends `{id, kind, repo, issue, time}` to `inbox.json`, keeping every entry whose ID is absent from `watched.json` plus the newest 200 printed entries. Only printed entries count toward the cap; the oldest printed entries drop first. Accepted replies leave the queue; `plans.json` saves approval envelopes under `<repo>#<issue>` and `answers.json` saves answer envelopes under the question ID. `next` adds `plan approved` or `plan needs changes` when a saved decision matches the current assignment epoch.

`qc fleet show <message-id>` finds the envelope ID in the queue, plans or answers and prints kind, sender, issue, epoch and text (the note for approvals). `qc watch --fleet` checks every 5 seconds: on the Leader it reports queued plans and questions; on a follower it reports unprinted IDs from `inbox.json`, so two approvals between polls produce two events even when they replace the same saved plan decision. It prints `EVENT fleet:<kind> <message-id>` once per ID, saves printed IDs in `watched.json`, and exits 0 after reporting new events. Later invocations skip saved IDs; the usual `--max` bound and timeout exit code 4 apply.
