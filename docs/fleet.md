# Split work across PCs
Fleet assigns free open issues across PCs on the LAN. Install `architecture-harness` and authenticate `gh` on each PC. Run init with no flags on each PC to get a random four-character hex name. Use the printed `fleet init --secret <hex>` command on the other PCs so they share the first PC's secret; add `--force` if already initialized. Start the Leader on one PC, and use `fleet start` on the others:

```sh
npx architecture-harness fleet init
npx architecture-harness fleet start --leader
npx architecture-harness fleet status --repo shawrylk/architecture-kit
npx architecture-harness fleet next --repo shawrylk/architecture-kit
```

Discovery sends signed UDP beacons at start and every 15 seconds. The firewall must allow UDP 47913 and the TCP node port (8080 by default; set `init --port <port>`). Optional `discoveryPort` changes the UDP port on all PCs. Each beacon advertises the IPv4 address returned by the bound HTTP server, including when the configured self address is a hostname, and goes to 255.255.255.255 and that interface’s broadcast address. If the bound address is not IPv4, no beacon is sent and `fleet discovery needs an IPv4 node address` is logged once. Peers expire after 300 seconds; `<git common dir>/qc/fleet/discovered.json` stores `{fleet: <first 16 hex of sha256(secret)>, nodes: {...}}`. A changed secret or old cache shape starts empty; the next save replaces it. Discovered leader IDs are sorted. A duplicate name reports `fleet name <id> is used by <address>`; reinitialize one PC with `--force --self <new-id> --secret <hex>`. `init --nodes` requires `--self`. For static settings, use `npx architecture-harness fleet init --self a1 --nodes a1:1:L,b2:1:L,c3:2:L --addresses a1@host:8080,b2@other:8080,c3@third:8080` and repeat with only `--self` changed. Static files keep working; `discover: true` enables discovery and fills a missing self address with the first local IPv4.

Keep the same static `nodes` on all PCs. Weight 2 receives about twice as much work as weight 1; `maxSize` is S, M or L and `active` defaults to true. Labels `size:S`, `size:M` and `size:L` ignore case; an issue without one is M. `next` prints this PC's oldest five free issue numbers; `--all` prints every one. It exits 3 when none remain; errors exit 1. `status` starts with `name=<self> discover=on|off`, then prints weight, maxSize, active, free count and up to ten numbers for up to 14 nodes, taken/unassigned counts, and `node=running|stopped|stale leader=<id or unknown> peers=<seen in 90 s>/<other nodes>`. `QC_FLEET_FILE` overrides the settings path; without a file fleet is off. `--repo` defaults to origin. Otherwise Windows uses `%APPDATA%\qc\fleet.json`; other systems use `$XDG_CONFIG_HOME/qc/fleet.json` or `~/.config/qc/fleet.json`. `init` creates parent folders and uses mode 0600 on POSIX; an existing file needs `--force` to replace it.

Optional `secret` is shared hex text of at least 64 characters; `init --secret <hex>` reuses it, otherwise init generates 32 random bytes and prints a line to pass the same secret on the other PCs. Optional `leaders` lists node IDs in preference order (default: node order). Each node may have `address` (a host other than `0.0.0.0` or `::`) and `port` (1024–65535); set these with `--addresses a1@host:8080,b2@[::1]:8081`. Old files remain valid. HTTP and discovery signatures use the full secret text as a UTF-8 HMAC key. Signed messages are data; local state stays in `<git common dir>/qc/fleet/`. `npx architecture-harness fleet start [--leader]` detaches `npx architecture-harness fleet serve`, logging to `<state dir>/node.log`; it needs a secret and this node's address (port defaults to 8080), passes a random instance token to the child, saves it with the PID in `node.json`, waits up to 5 seconds for matching health, and succeeds if that instance is already running. `status` and `stop` require health to match the saved instance; a mismatch reports `stale` and leaves the process alone. `npx architecture-harness fleet stop` waits up to 5 seconds for exit and removes only `node.json`. Other state survives, including `outbox.json` and `peers.json`. `serve [--leader]` also runs in the foreground.

Free issues exclude `hold`, `merge.holdLabel` and `fleet-skip`. An open PR body naming `#<number>`, a PR head branch, or an origin branch named `<prefix>/<number>-...` makes an issue taken. Reads use `gh` and git, bounded to 500 open issues and 200 open PRs. No qualifying active node means unassigned. Only a matching local checkout supplies `merge.holdLabel` from `qc.config.json`. The server binds only its configured address. `GET /health` returns `{"ok":true,"instance":"<token>"}`; `POST /message` checks signatures and saved replay IDs, accepts up to 64 KB with 202, puts work messages into `queue.json`, and never runs commands. Requests time out after 10 seconds; shutdown stops accepting requests and force-closes open connections after 1 second. Other routes return 404; bad messages return 400 and oversized bodies 413. For free-issue suggestions without a Leader, set `active: false` on every PC to redistribute that node's suggestions. With a Leader, saved assignments can move automatically when a worker goes silent. Push the usual issue branch when starting work so subsequent free-issue reads see it as taken. Every 30 seconds, heartbeats send `{ kit: <kit commit or null>, leader: <boolean>, term: <positive integer>, work: [...] }` to other active addressed nodes. Every heartbeat, including a follower’s, carries the highest term the sender has seen. A Leader receiving any heartbeat above its own term immediately saves `leader: false` and the higher term in `node.json`. Before each assignment tick, Leader send and resend, the serve loop rereads the saved role and term; it checks again after each await before the next action. `work` contains `{repo, issue, epoch, step, branch, head}` for every assignment held by the sender; unset progress fields are null. A Leader also sends `assigned: [{repo, issue, epoch}]` for the receiving node. Immediately before each send, the node rebuilds the full heartbeat body from fresh synchronous reads of its role, term, assignments and work, so confirmation during an earlier send cannot advertise a stale assignment list. `peers.json` keeps each node’s latest receipt time, signed heartbeat `time` as `messageTime`, and heartbeat fields. Every valid heartbeat updates the receipt time; liveness uses only that receipt time. Within a term, a heartbeat whose signed time is older than or equal to the saved one preserves `messageTime` and the snapshot fields (`leader`, `kit`, `assigned`, `work`); a higher term replaces an older term regardless of signed time, and a lower term cannot replace an accepted snapshot; heartbeats never enter `queue.json`. State files are `assignments.json`, `questions.json`, `seen.json`, `queue.json`, `outbox.json`, `dead.json`, `peers.json`, `work.json` and `node.json`. Sends time out after 5 seconds; network errors and 5xx replies enter `outbox.json` and retry oldest first after 1 second, doubling to 60 seconds. The outbox stores unsigned fields and a fixed ID; every send signs again with the current time. A 4xx reply removes the entry: `seen-id` counts as delivered; other refusals enter `dead.json`, which keeps only the last 100.

With `serve --leader`, an assignment tick runs every 60 seconds. It reads `freeIssues` and open issue numbers through `gh`; a failed read skips that tick. The Leader saves `{repo, issue, node, epoch: 1, time, size}` records keyed by `repo#issue` in `assignments.json`, retaining each until its issue closes or its owner is replaced. GitHub labels stay unchanged. It considers `ci-red` issues first, then the lowest issue number, using `ownerOf(repo, issue, size, idle live nodes)` and skipping issues with no owner. Each node gets one issue at a time. Other nodes must be active, addressed, and have a heartbeat less than 90 seconds old; the Leader itself is always live. A different heartbeat kit blocks new work and warns `node <id> runs kit <k>, leader runs <k>`. On every 60-second assignment tick, the Leader sends an `assign` message with `{issue, epoch}` (plus `branch` and `head` when resuming work) for each current assignment to another live node, including previously sent assignments. It skips a repeat when that node already has an `assign` for the same repository, issue and epoch in `outbox.json`. The Leader writes all these messages to the outbox before sending any of them, then flushes the outbox. Stopping during a send leaves unconfirmed assignments queued for retry. Every node tick accepts only positive integer issues and epochs from a peer whose latest heartbeat says `leader: true`; a higher epoch replaces a lower one once the latest Leader heartbeat lists it. An assign arriving before its matching heartbeat waits in the queue for up to 10 minutes; it cannot delete the currently confirmed epoch. The same issue and epoch is ignored without changing the saved assignment. An assign arriving before that peer has a Leader claim stays in `queue.json` until a heartbeat claims leadership. With no claim it expires after 10 minutes from its message time; a `leader: false` heartbeat drops it at once on the next node tick. The Leader sends a fresh message on the next assignment tick, so an unclaimed assignment dropped after 10 minutes can arrive again. Other queued message kinds remain. Every 60 seconds, a follower reads `gh issue list --state open` for each repository where it holds assignments and removes its own assignments whose issues have closed. A failed or unreadable gh response preserves that repository's assignments. After a Leader heartbeat arrives, each follower tick also drops its own assignments missing from that latest Leader’s `assigned` list at the saved epoch. Before any Leader heartbeat arrives, it keeps its assignments. The serve loop and explicit Leader confirmation write `assignments.json`. `npx architecture-harness fleet next` reads the file and makes the same open-issue check to hide closed issues from its output without writing the file. On a gh error it uses the saved assignments unchanged. It prints open saved assignments for this node and repository first as `#<issue> epoch=<n>`; with none, its usual free-issue output applies. Plan approval and failover follow the rules below.

When a non-Leader owner has no heartbeat for 90 seconds or more, the next assignment tick moves its work before assigning new issues. If a node has never sent a heartbeat, the 90-second wait starts at its assignment time. The Leader uses `ownerOf` among idle live nodes with a matching kit and sufficient size, and increments the epoch by one. Saved sizes remain available even when an issue is already taken by a branch; legacy assignments without a size default to M. If no idle compatible node is available, the assignment stays with its old owner and the tick warns `#<issue> waits: node <id> is dead`. Leader death uses the confirmation flow below.

`npx architecture-harness fleet progress 242 --step plan|code|review|merge [--branch feat/242-work] [--head <sha40>]` needs this node’s saved assignment and an origin repository. It saves `{repo, issue, epoch, step, branch, head}` in `work.json` under `<repo>#<issue>`. Omitted branch/head values keep the previous progress at that epoch; a new epoch starts with null values. It makes no GitHub changes. Heartbeats carry this progress to the Leader. On takeover, the Leader copies available branch/head values only from the dead node’s last work entry matching the repository, issue and old epoch, then the follower saves them with its new assignment.

`npx architecture-harness fleet next` prints a resumed assignment as `#242 epoch=2 from feat/242-work@<sha40>`. Fetch that head with `git fetch origin <sha40>` and start a new branch with `git switch -c feat/242-takeover <sha40>`. Record the new branch with `npx architecture-harness fleet progress 242 --step code --branch feat/242-takeover --head <sha40>`. Do not reuse or force-push the dead node’s branch.

Before **each push**, the session must run `npx architecture-harness fleet owns 242` and push only if it exits 0. It succeeds only when the latest Leader heartbeat lists this node’s repository/issue at its saved epoch. Missing assignments, no Leader heartbeat, a missing list entry or a different epoch print a reason and exit 1. The Leader records its own heartbeat snapshot locally so its sessions use the same check. If ownership is lost, stop work and do not push. `owns` checks local heartbeat state, so run it immediately before the push; it is not a remote lock. On each node tick, an outbox work message falls back to GitHub after three failed sends, or when its destination has no recorded heartbeat or its last heartbeat is at least 90 seconds old. Work kinds are `assign`, `plan`, `approve`, `question`, `answer`, `pushed`, `verdict`, `platform-check` and `platform-result`; the body must contain a positive integer `issue`. Heartbeats and election messages never use GitHub. Eligible messages bypass HTTP retry backoff. The node signs the same message ID again with the current time and posts on that issue in the message's repository through `roleComment`, as Leader on the Leader and Coder elsewhere, with summary `<kind> for #<issue>`. The comment body contains only `<!-- qc:msg to=<node-id> <base64url of the signed message JSON> -->`, surrounded by the role heading and authenticated role marker. A successful post removes the entry; a failed post retains it for the next tick. Every 120 seconds, each node reads all issue comments in its serve repository and each repository with a saved assignment, once per repository. This lets a follower discover its first `assign` without already holding an issue. Each read uses `gh api --paginate repos/<repo>/issues/comments?per_page=100&since=<cursor>`. `github.json` saves one cursor per repository: the newest comment `updated_at` from GitHub minus 60 seconds. The first read without a cursor uses local time minus 10 minutes. Empty reads and gh errors preserve the cursor. The overlap repeats comments; the shared seen-ID check drops repeats silently. Only comments authored by the current gh user, accepted by `parseMarker`, and addressed to this node qualify. The decoded work message must match the comment's sender, kind, repository and issue from `issue_url`, then pass the same signature, known-sender, time and saved-ID checks as HTTP receipt. Both transports share `seen.json` and `queue.json`, so a message delivered over both is processed once. Authenticate all nodes with the same GitHub account.

`npx architecture-harness fleet plan <issue> --file <path>` and `npx architecture-harness fleet ask <issue> --file <path>` require an issue held by this node. Files hold at most 20000 characters. Both send `{issue, epoch, text}` to the peer whose heartbeat says `leader: true`; plan sends kind `plan` and posts a signed Coder role comment with kind `plan` and ref `#<issue>`, while ask sends kind `question` and posts nothing. Both write the message to `outbox.json` before any network send, then call `flushOutbox`; the plan comment follows the outbox write. Commands print their message IDs. `npx architecture-harness fleet approve <message-id> [--changes] [--file <note>]` runs on the Leader only. It sends `{issue, epoch, plan: <id>, approved: !changes, note}` to the plan sender and posts a signed Leader role comment of kind `approve`. Without a file the note is empty; `--changes` requests changes. `npx architecture-harness fleet answer <message-id> --file <answer>` runs on the Leader only. It sends `{issue, epoch, question: <id>, text}` to the question sender and posts a signed Leader role comment of kind `answer` with every question line quoted. Before either reply reads a file, posts a comment or sends a message, it checks the request by the same rule as the Leader tick: the sender must hold that repository and issue at that epoch in the Leader assignments. A failed check drops the request, prints the reason and exits 1 without a comment or send. Both replies remove the request from the Leader queue; transient send failures use the durable outbox. A failed comment leaves the request queued. Each Leader tick drops plans and questions unless the sender holds that repository, issue and epoch. Followers apply the `assign` sender rule to approvals and answers: unknown Leader claims wait up to ten minutes, explicit false claims drop replies. Wrong epochs or issues not held by this node drop immediately. Each accepted reply also appends `{id, kind, repo, issue, time}` to `inbox.json`, keeping every entry whose ID is absent from `watched.json` plus the newest 200 printed entries. Only printed entries count toward the cap; the oldest printed entries drop first. Accepted replies leave the queue; `plans.json` saves approval envelopes under `<repo>#<issue>` and `answers.json` saves answer envelopes under the question ID. `next` adds `plan approved` or `plan needs changes` when a saved decision matches the current assignment epoch.

`npx architecture-harness fleet show <message-id>` finds the envelope ID in the queue, plans or answers and prints kind, sender, issue, epoch and text (the note for approvals). `npx architecture-harness watch --fleet` checks every 5 seconds: on the Leader it reports queued plans and questions; on a follower it reports unprinted IDs from `inbox.json`, so two approvals between polls produce two events even when they replace the same saved plan decision. It prints `EVENT fleet:<kind> <message-id>` once per ID, saves printed IDs in `watched.json`, and exits 0 after reporting new events. Later invocations skip saved IDs; the usual `--max` bound and timeout exit code 4 apply.

The first Leader has term 1. Followers accept Leader claims only at or above their highest observed term; a Leader that sees any higher-term heartbeat, including a follower’s, immediately saves the higher term and steps down before its next action. After 90 seconds without a Leader heartbeat, the candidate is the first live ID in `leaders` order (this node counts as live). It sends `propose-leader {term: highest + 1}` to every live peer. A peer votes once per term and replies `leader {term, accept: true}` only when it also sees the Leader dead. Followers keep working on their held issues during an election. One live peer's accept saves `proposal.json`. `npx architecture-harness fleet status` prints `proposed Leader <id> term <t>: run npx architecture-harness fleet confirm-leader`; `npx architecture-harness watch --fleet` prints `EVENT fleet:propose-leader <term>` once per term. Run `npx architecture-harness fleet confirm-leader` on that candidate to become Leader at the proposal term. With exactly two nodes, confirmation needs no proposal once the Leader is dead. Confirmation rebuilds `assignments.json` from live nodes' work snapshots, including local work, keeping the highest epoch per issue and its owner and progress. The running server reads its role from `node.json` every tick. Terms and votes survive restarts in `election.json`. A Leader with no live peer for 90 seconds pauses assignment until a peer returns.

After pushing an assigned branch, run `npx architecture-harness fleet pushed <issue> --branch <branch> --head <40-character SHA>`. This uses the same ownership check as `npx architecture-harness fleet owns`: the local assignment and the latest Leader's assignment snapshot must name this node and the same epoch. It queues `pushed {issue, epoch, branch, head}` to the Leader. Every heartbeat now includes `os` from `hostOS()` (`windows`, `darwin` for macOS, or `linux`), saved with the peer snapshot. The Leader accepts a pushed head only from the issue's holder at that epoch. It fetches the branch and evaluates `platformRisk` against `check.base`. When risk is present, it chooses the lowest live node ID for each OS in `ready.platforms`, excluding the pusher's OS, and sends `platform-check {issue, epoch, branch, head, pusher}`. A missing OS prints `no live <os> node for #<issue>`. Configure `ready.platforms` with any distinct combination of `linux`, `windows`, and `darwin`; these platforms also accept passing legs from `source: "fleet"`.

A node accepts platform checks only from its current Leader. Branches must match `^[A-Za-z0-9._/-]+$` and cannot begin with a dash; heads must be 40 hex characters. Checks run one at a time: fetch the branch, create a temporary detached worktree at the requested head, run this installed kit's `npx architecture-harness check --affected --base origin/main` there with a 30 minute limit, and remove the worktree afterward. The check runs as a child process while the node continues heartbeats. Only run fleet checks for repositories and pushed code you trust to execute on these PCs. Every check exit, timeout, or node shutdown stops the check's process tree. On POSIX, the node sends SIGKILL to the process group; a check that leaves a live child fails with `check left a child process`, even after exit 0. On Windows, the node uses `taskkill /pid <pid> /t /f`; after a normal exit, Windows cannot find orphaned descendants through that tree, so they cannot be detected or stopped this way. Before reporting a pass, the node verifies the requested HEAD and a clean worktree, including untracked files even when `status.showUntrackedFiles=no`.

The node sends `platform-result {issue, head, os, ok, tail}` to both the pusher and the Leader; `tail` contains at most the last 40 output lines, with very long output truncated to fit the transport limit. The pusher accepts results only when the sender's heartbeat OS matches, and a pass appends `{os, head, source: "fleet"}` to the shared leg ledger. Readiness counts that leg for the matching head. The Leader posts each accepted result as a signed Reviewer comment of kind `platform-result`, with `platform check on <os>: pass|fail` and the output tail in a code block. Failed comment posts remain queued for retry.
Heartbeats include `load: {cpu, mem, rtt}`: CPU busy fraction since the previous sample (null initially), memory used fraction, and median milliseconds of successful sends in the last completed heartbeat round (null if none succeeded). Fractions round to two decimals. At CPU or memory >= 90%, or RTT >= 2000ms, a node including the Leader keeps its held issue but receives no new issue or takeover; the tick warns with every overload reason. Status adds `load <id> cpu=<n>% mem=<n>% rtt=<n>ms` for each peer seen within 90 seconds, using `-` for unknown values and appending ` overloaded` at a limit.
